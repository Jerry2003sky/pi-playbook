# 高阶阶段：子代理与剪枝

本阶段的两个插件对 pi 改动最深（定位见 [01-理念与路线.md](01-理念与路线.md)）：子代理带来多代理并行和上下文隔离，剪枝把上下文占用从线性增长压到基本持平。两者都改变了 pi 的工作方式，代价也最明显：子代理要管权限边界，剪枝会让历史细节默认不可见、打断提示缓存。它们放在最后，是因为要靠前面几个阶段打底——比如剪枝的效果要靠缓存监控来验证。

本页内容：**@tintinweb/pi-subagents**（子代理系统）· **pi-condense**（上下文剪枝）

## @tintinweb/pi-subagents —— 子代理系统

> 商店：[pi.dev/packages/@tintinweb/pi-subagents](https://pi.dev/packages/@tintinweb/pi-subagents) · 仓库：[tintinweb/pi-subagents](https://github.com/tintinweb/pi-subagents)

pi 默认单模型、单会话，决策和执行挤在同一个上下文里。任务一大，机械执行的部分会吃掉大量上下文和 token，还会干扰决策。

pi-subagents 引入子代理。主代理用 `Agent` 工具把任务派给另一个独立会话，能力包括：

- 前台阻塞、后台异步、并行执行、定时调度；
- 子代理可以再委托（嵌套）；
- 用 git worktree 隔离代码改动；
- 在输入框里用 `@代理名` 直接点名；
- 运行中途用 `steer_subagent` 纠偏。

批量任务的规模要到运行时才知道时，用 `SubagentWorkflow`：模型写一段确定性的 JavaScript 脚本，用 `agent()`、`parallel()`、`pipeline()` 把子代理串成多阶段流水线。

“便宜模型做执行”靠这套机制落地：大任务里的机械部分交给 flash 级子代理，主模型负责决策和汇总。独立会话隔开了上下文，worktree 可以隔开代码改动；工具执行的权限仍然等同于本机进程的系统权限。

安装：

```bash
pi install npm:@tintinweb/pi-subagents@0.19.0
```

0.19.0 要求 Pi 0.84.0 或更新版本。

配置分两层：

- **持久设置**：全局 `~/.pi/agent/subagents.json`，项目里的 `.pi/subagents.json` 可以覆盖。
- **自定义代理**：每个代理一个 Markdown 文件，YAML frontmatter 定义属性，正文就是它的 system prompt。可以放在 `.pi/agents/<name>.md`（项目级，优先级最高）、`.agents/agents/<name>.md`（项目级共享目录）或 `~/.pi/agent/agents/<name>.md`（全局）；同名时项目级覆盖全局。

**我的配置**：没有 subagents.json，持久设置全用默认值——后台并发 10、前台不限、嵌套深度 2、兜底代理 general-purpose、未指定时后台运行、工作流自动判断。

唯一的自定义是 `pico` 执行代理（[`config/agents/pico.md`](../config/agents/pico.md)）：模型固定为 deepseek 的 `deepseek-flash`，thinking high，`prompt_mode: replace`，不开嵌套委托。它的 `tools` 覆盖了子代理插件识别的全部七个内置工具，所以 Agent 工具描述里显示为 `*`；扩展工具单独加载，嵌套委托由 `allowed_subagents` 控制。设计细节见 [08-agents.md](08-agents.md)。

### 常用参数

| 参数 | 位置 | 作用 |
|------|------|------|
| `maxConcurrent` | subagents.json | 后台代理并发上限（默认 10） |
| `maxConcurrentForeground` | subagents.json | 前台阻塞代理并发上限（默认 0 = 不限） |
| `backgroundByDefault` | subagents.json | 未写 `run_in_background` 的顶层派发是否后台运行（默认 true） |
| `workflowsEnabled` | subagents.json | 是否注册 `SubagentWorkflow`（默认 true，未设置时自动避让其他工作流工具） |
| `maxSubagentDepth` | subagents.json | 嵌套委托深度上限（默认 2），`0` / `1` 全局关嵌套 |
| `fallbackSubagent` | subagents.json | 类型名解析失败时的兜底，`none` 是严格模式直接报错 |
| `model` | 代理 frontmatter | 该代理用的模型，成本控制的第一旋钮 |
| `tools` | 代理 frontmatter | 限定可用的内置工具；插件工具另用 `ext:<扩展>` 前缀筛选 |
| `allowed_subagents` | 代理 frontmatter | 嵌套委托白名单，不开则子代理不能再派发 |

### 参数详解

#### 持久设置（subagents.json）

全局文件 `~/.pi/agent/subagents.json` 手写；`/agents → Settings` 里的改动写进项目的 `.pi/subagents.json`，同名字段项目覆盖全局。文件缺失时静默用默认值，JSON 写坏时 stderr 警告并忽略整个文件，单个字段值非法时只丢弃该字段。“生效时机”一列：即时 = 改完马上生效；下次会话 = 涉及工具定义，重启 Pi 后才生效。

并发与轮数：

| 参数 | 默认 | 取值与效果 |
|------|------|-----------|
| `maxConcurrent` | `10` | 后台代理同时运行的上限，超出的排队，有空位再启动。嵌套子代理和 `SubagentWorkflow` 派出的代理不占这个名额 |
| `maxConcurrentForeground` | `0` | 前台（阻塞等待结果）代理的并发上限，`0` = 不限。同一条消息里的多个前台 `Agent` 调用默认会同时启动，本地模型并发容易互相挤掉缓存，这时可以设个上限。与后台池分开计算 |
| `defaultMaxTurns` | `0` | 代理默认的轮数上限，`0` = 不限。代理 frontmatter 写了 `max_turns` 时以它为准 |
| `graceTurns` | `5` | 到达轮数上限后，先发一条“立即收尾”的指令，再给这么多轮完成收尾；超过仍未结束才强制中止（状态记为 `aborted`），按时收尾的记为 `steered` |
| `maxSubagentDepth` | `2` | 嵌套委托的最大深度：主会话 = 0，它派出的子代理 = 1，子代理再派出的 = 2。`0` 或 `1` 等于全局关闭嵌套，无论代理是否配置了 `allowed_subagents`。对之后启动的代理生效 |

派发行为：

| 参数 | 默认 | 取值与效果 |
|------|------|-----------|
| `backgroundByDefault` | `true` | 只决定 `Agent` 调用没写 `run_in_background` 时怎么跑：<br>`true`：后台运行，调用立即返回代理 ID，完成后发通知（附结果预览，全文用 `get_subagent_result` 取）<br>`false`：前台运行，主会话阻塞等它跑完，结果直接作为工具返回值<br>调用参数或 frontmatter 显式写了 `run_in_background` 时以它们为准。嵌套派发始终前台。即时生效 |
| `defaultJoinMode` | `smart` | 多个后台代理完成时怎么通知主会话：<br>`"smart"`：同一轮里派出的 2 个及以上后台代理合并成一条通知，单个的单独通知<br>`"async"`：每个代理完成就单独通知一次，适合要边到边处理结果的场景<br>`"group"`：即使只派了一个也按组等待合并，适合知道后面还会追加代理的场景<br>合并时，第一个完成后最多再等 30 秒，没到齐就先发已完成的部分，剩下的按 15 秒窗口补发 |
| `fallbackSubagent` | `general-purpose` | `subagent_type` 解析不到唯一一个启用的代理（名字不存在、已禁用、或只差大小写的重名）时的处理：<br>`"general-purpose"`：改派给它（宽松模式，默认）<br>其他代理名：改派给那个代理<br>`"none"`（或布尔 `false`）：严格模式，直接报错并列出可用类型，什么都不启动。后台和定时任务尤其建议用严格模式，否则可能先跑起一个替补代理，调用方才知道出了错 |
| `schedulingEnabled` | `true` | `true`：`Agent` 工具带 `schedule` 参数，可按 cron / 间隔 / 定时派发<br>`false`：从工具定义里删掉 `schedule`（省上下文），停掉调度器，隐藏 `/agents → Scheduled jobs`。删参数要下次会话生效，停调度即时生效 |
| `agentMentions` | `model` | 输入框里 `@代理名 消息` 的行为。运行中的代理收到消息、已结束的代理被续跑，这两种情况在 `model` 和 `direct` 下相同；区别在于点名一个还没启动的代理：<br>`"model"`：复制当前对话到后台，由模型调用 `Agent` 启动它，代理的 prompt 由模型根据对话写。会重发整段对话，启动前有一次模型调用的延迟<br>`"direct"`：立刻启动，你输入的原话就是它的 prompt，不调模型；但不写 `.output` 转录<br>`"off"`：关闭，`@` 只用于附加文件<br>旧的布尔写法仍可用：`true` = `model`，`false` = `off`。即时生效 |
| `workflowsEnabled` | 未设置（自动） | 不写：自动模式，默认注册 `SubagentWorkflow`，但如果别的扩展已提供 `Workflow` / `SubagentWorkflow` 工具，本扩展让位<br>`true`：始终注册，不管别的扩展<br>`false`：不注册，模型不知道这个功能，`/agents → Workflows` 隐藏，`--subagents-workflow-file` 被拒绝<br>下次会话生效 |
| `worktreeIsolation` | `true` | `true`：允许 `isolation: "worktree"` 创建 git worktree<br>`false`：`Agent` 工具里的 `isolation` 参数和对应说明一起移除；任何途径（frontmatter、定时任务、跨扩展调用）请求 worktree 都静默降级为在主工作区运行，不报错。仓库很大、复制一份代价高时关掉。参数移除下次会话生效，拒绝创建即时生效 |
| `scopeModels` | `false` | `true`：按 settings.json 的 `enabledModels` 校验子代理用的模型。调用方传入范围外的模型直接报错；frontmatter 钉死的、继承父会话的模型只弹警告照常运行。`enabledModels` 只认精确的 `provider/modelId`，为空时不校验<br>`false`：不校验，子代理可用任何模型 |

代理注册：

| 参数 | 默认 | 取值与效果 |
|------|------|-----------|
| `disableDefaultAgents` | `false` | `true`：不注册内置的 general-purpose、Explore、Plan 三个代理，只剩自定义代理。注意兜底仍是 `general-purpose`，此时会落到一个带全部工具的内置配置上，想彻底关掉要配合 `fallbackSubagent: "none"`<br>`false`：内置三个代理照常注册。下次会话生效 |
| `strictAgentFiles` | `false` | `true`：启动时有代理文件读不了或解析失败，直接让 pi 启动失败并报出文件名<br>`false`：跳过坏文件并警告，如果它本来覆盖了同名代理，就会用到另一个位置的同名文件。会话中途重新加载时始终只警告 |
| `rememberAgents` | `true` | `true`：子代理的会话存成普通 pi 会话文件，在 `/resume` 里挂在父会话下面；代理结束很久后还能用 `@代理名` 重新打开继续聊<br>`false`：会话只在内存里，代理结束约 10 分钟后记录清除，再 `@` 就是启动新代理<br>代理 frontmatter 的 `persist_session` 可单独覆盖 |
| `outputTranscript` | `true` | `true`：每个子代理把完整对话写一份 JSON-lines 转录到系统临时目录（`<tmp>/pi-subagents-<uid>/.../tasks/<id>.output`，仅本人可读，重启清空）<br>`false`：不写转录，适合不希望运行记录落盘的项目。只管转录，不影响会话持久化、worktree 和代理记忆。frontmatter 的 `output_transcript` 可单独覆盖 |
| `toolDescriptionMode` | `full` | 主模型看到的 `Agent` 工具描述：<br>`"full"`：完整描述（默认代理下约 1400 token）<br>`"compact"`：精简版，约小 75%，适合小模型或本地模型<br>`"custom"`：读 `.pi/agent-tool-description.md`（项目）或 `~/.pi/agent/agent-tool-description.md`（全局），支持 `{{typeList}}` 等占位符；文件缺失或为空时回退 `full`<br>下次会话生效 |

界面与统计：

| 参数 | 默认 | 取值与效果 |
|------|------|-----------|
| `widgetMode` | `background` | 输入框上方的代理状态挂件：<br>`"background"`：只显示后台、排队、定时的代理；前台代理已经在工具结果里实时显示，不重复显示<br>`"all"`：所有代理都显示<br>`"off"`：隐藏挂件 |
| `fleetView` | `true` | `true`：输入框为空时按 `↓` 进入下方的代理列表，选中后回车打开该代理的实时对话，可直接给它发消息纠偏<br>`false`：不显示列表，也不占用方向键 |
| `showModel` | `false` | `true`：挂件里每个运行中的代理显示所用模型和思考档位<br>`false`：不显示（窄终端下给描述留位置）。工具结果和对话查看器里始终显示 |
| `showCost` | `false` | `true`：挂件、代理列表、完成通知等处在 token 数旁显示估算花费（如 `~$0.0042`），没有定价数据的模型不显示<br>`false`：只显示 token |
| `reportUsage` | `false` | `true`：把子代理的花费计入本会话统计，pi 底栏和 `/cost` 会包含子代理的消耗（归在 Tools/summaries 一栏）<br>`false`：本会话统计只算主模型，委托很多的会话看起来几乎不花钱。与 `showCost` 互不影响：一个管统计口径，一个管界面显示 |
| `viewerMarkdown` | `assistant` | 子代理对话查看器里哪些内容按 Markdown 渲染：<br>`"off"`：全部原样显示<br>`"assistant"`：只渲染助手回复，工具输出原样显示<br>`"all"`：工具输出也渲染。shell 脚本的 `#`、日志里的 `---` 会被当成标题，只适合工具本身输出 Markdown 的场景<br>查看器里按 `m` 循环切换，选择会写回这个字段 |

#### 自定义代理 frontmatter

全部字段可选。frontmatter 说了算：文件里写了 `model`、`thinking`、`max_turns`、`inherit_context`、`run_in_background`、`isolated`、`isolation`，主模型调用 `Agent` 时传的同名参数无法覆盖。

身份与显示：

| 参数 | 默认 | 取值与效果 |
|------|------|-----------|
| `name` | 文件名 | 代理类型名，也就是 `subagent_type` 和 `@` 点名用的名字，不能含 `:` |
| `display_name` | 同 `name` | 只改界面上显示的标签 |
| `description` | 文件名 | 出现在 `Agent` 工具代理列表里的说明，主模型据此决定派给谁 |
| `color` | 无 | 名字徽章的底色：`red` / `blue` / `green` / `yellow` / `purple` / `orange` / `pink` / `cyan`，带引号的 `"#RRGGBB"`，或 `teal`、`indigo` 等别名；非法值不显示徽章 |
| `enabled` | `true` | `false`：禁用这个代理，常用来在某个项目里隐藏内置代理 |

模型与运行：

| 参数 | 默认 | 取值与效果 |
|------|------|-----------|
| `model` | 继承父会话 | `provider/modelId` 或模糊名（如 `haiku`）。匹配宽松：`.` 和 `-` 视为相同，日期后缀可省，指定的供应商没有这个模型时会找其他供应商的同名模型；都找不到就继承父会话模型 |
| `thinking` | 继承父会话 | `off` / `minimal` / `low` / `medium` / `high` / `xhigh` / `max`；模型不支持的档位会被 pi 往下调 |
| `max_turns` | 不限 | 轮数上限，`0` 或不写 = 不限；到达后按 `graceTurns` 收尾 |
| `prompt_mode` | `replace` | `replace`：正文就是完整系统提示，不继承 AGENTS.md / CLAUDE.md，代理只知道正文写的内容<br>`append`：正文追加在父会话系统提示之后，代理继承 AGENTS.md 等全部全局指令 |
| `inherit_context` | `false` | `true`：把父会话的对话历史复制给代理，它知道之前聊过什么，但启动更贵<br>`false`：代理从空白会话开始，只看到派发时的 prompt |
| `run_in_background` | 不写 | `true`：总是后台运行<br>`false`：总是前台运行<br>不写：跟随 `backgroundByDefault` 和调用参数 |
| `isolation` | 不写 | `worktree`：在临时 git worktree 里运行。没有改动则清理掉；有改动则提交到 `pi-agent-<id>` 分支，结果里给出合并命令。worktree 看不到主工作区未提交的改动，不能用来审查当前 diff；有 shell 权限的代理仍能 `cd` 出去，它不是沙箱<br>`off`（也可写 `none` / `no` / `false`）：拒绝 worktree，调用方要求了也不建<br>不写：由调用参数决定 |

工具、扩展与技能：

| 参数 | 默认 | 取值与效果 |
|------|------|-----------|
| `tools` | 全部 7 个内置工具 | 内置工具名列表，如 `read, grep, find`；`*` 或 `all` = 全部内置工具；`none` = 不给内置工具。加 `ext:<扩展>` 或 `ext:<扩展>/<工具>` 筛选扩展工具：只要写了任何一个 `ext:`，就只暴露点名的扩展工具，其他扩展照常加载但不暴露工具。写错工具名会报错 |
| `extensions` | `true` | `true`：加载所有默认扩展<br>`false`：不加载任何扩展<br>列表，如 `[mcp, "/abs/path.ts", "*"]`：只加载列出的（`*` 表示全部默认扩展）<br>它决定加载哪些扩展，`tools` 里的 `ext:` 只能在已加载的里面筛选 |
| `exclude_extensions` | 无 | 在 `extensions` 之后排除的扩展名（不区分大小写，不支持路径和 `*`），优先级最高。被排除的扩展加载代码仍会执行一次，不能当安全隔离用 |
| `skills` | `true` | `true`：继承父会话的技能<br>`false`：不加载技能<br>列表：只把列出的技能预加载进系统提示，其余不继承 |
| `disallowed_tools` | 无 | 禁用的工具名列表，扩展提供的也禁 |
| `isolated` | `false` | `true`：封闭专家模式，等于 `extensions: false` + `skills: false`，并忽略 `ext:` 选择，只剩内置工具；也不会拿到嵌套委托工具<br>`false`：正常加载。它管的是扩展和技能，跟管文件系统的 `isolation: worktree` 是两回事 |
| `allowed_subagents` | 不允许 | 是否允许这个代理再派子代理：<br>不写、空、`none`、`false`：不注入嵌套工具<br>`all`、`"*"`、`true`：可派发任何启用的代理<br>代理名列表：只能派发列出的类型<br>子代理按自己的 `tools` 运行，不继承父代理的限制，所以白名单等于把列出代理的全部能力授予父代理，要像选 `tools` 一样谨慎 |

会话与记忆：

| 参数 | 默认 | 取值与效果 |
|------|------|-----------|
| `memory` | 无 | 跨会话的代理记忆：<br>`project`：存 `.pi/agent-memory/<name>/`，随项目提交，团队共享<br>`local`：存 `.pi/agent-memory-local/<name>/`，本机专用（应加进 gitignore）<br>`user`：存 `~/.pi/agent/agent-memory/<name>/`，跨项目的个人记忆<br>没有 `write` / `edit` 工具的代理只能读不能写记忆 |
| `persist_session` | 跟随 `rememberAgents` | `true`：会话存成普通 pi 会话<br>`false`：只在内存里 |
| `output_transcript` | 跟随 `outputTranscript` | `true`：写 `.output` 转录<br>`false`：不写 |
| `session_dir` | pi 默认位置 | 持久化会话的存放目录，相对路径按代理工作目录解析 |

### SubagentWorkflow —— 脚本化编排

少量、事先就能确定的独立任务用 `Agent`；批量、多阶段的任务用 `SubagentWorkflow`，以 JavaScript 脚本编排。它可能一次派出大量子代理，所以使用约定要求：用户明确选择工作流或多代理编排后才运行。

**写法。** 脚本开头必须是纯字面量的 `export const meta = { name, description }`。三个核心函数：

- `agent()`：派发一个子代理；
- `pipeline()`：每一项独立地逐阶段推进；
- `parallel()`：等这一组全部完成再往下走。

优先用 `pipeline()`，只有需要跨项汇总时才用 `parallel()` 这道屏障。`schema` 校验子代理返回的对象，`gate` 用命令的退出码验证结果。

**运行限制。** 脚本在 worker thread 的 `node:vm` 里执行，不能读取当前时间、生成随机数或动态生成代码；需要时间戳就通过 `args` 传进去。并发上限 `max(1, min(16, cpus - 2))`，单次运行最多 1000 个代理，`parallel()` / `pipeline()` 单次最多 4096 项。工作流的并发池和会话的 `maxConcurrent` 相互独立。这些限制是为了保证重放结果确定，安全隔离仍要靠运行环境。

**观察与控制。** 调用后立即返回 task id，工作流在后台运行，完成后走普通的后台通知。`/agents → Workflows` 打开两层面板（阶段 → 代理 → prompt/activity/outcome），快捷键：`x` 停止、`p` 暂停、`s` 跳过（该次 `agent()` 返回 `null`）、`r` 重试、`c` 打开该子代理的对话。

**脚本复用。** 每次调用的脚本都会存到会话目录，改完用 `scriptPath` 重跑。值得保留的脚本放进 `.pi/workflows/`、`.agents/workflows/` 或代理目录的 `workflows/`，之后用 `name` 调用。`resumeFromRunId` 重放同一会话中某次已结束运行里没改动的前缀部分，只在该会话内有效。启动时也可以用 `--subagents-workflow-file=<path>` 直接跑一个脚本。

开关 `workflowsEnabled` 默认开启；不显式设置时处于自动模式，发现别的扩展已经提供了 `Workflow` / `SubagentWorkflow` 工具，就主动让位。

| 参数 | 说明 |
|------|------|
| `script` | 脚本源码 |
| `scriptPath` | 脚本文件路径，优先于 `script` 和 `name` |
| `name` | 已保存的脚本名，在三个 `workflows/` 目录里找 `<name>.js` |
| `args` | 原样传给脚本的 `args` 全局 |
| `resumeFromRunId` | 重放同一会话里某次已结束运行的未变前缀 |

`title` / `description` 两个参数接受但忽略，工作流名字以 `meta` 为准。

## pi-condense —— 上下文剪枝

> 商店：[pi.dev/packages/pi-condense](https://pi.dev/packages/pi-condense) · 仓库：[jjuraszek/pi-condense](https://github.com/jjuraszek/pi-condense)

上下文是长会话里最贵的资源。pi 默认让工具输出一直占着上下文：读过的大文件、跑过的命令、搜过的结果全堆在窗口里，越聊越贵、越聊越慢，最后触发 compact，把整个会话压成一段摘要——这是信息损失最大的处理方式。

pi-condense 改为逐批归档。每次 flush 时，已经用过的工具输出交给摘要模型压成简短的 stub，原文归档到会话本地的索引里；模型需要时，用 `context_tree_query` 按引用取回。历史细节平时不占上下文，要用时又拿得回来，上下文占用因此从线性增长变为基本持平，长会话才撑得下去。

代价有三项：

- 历史细节默认不可见，要靠模型主动按引用取回；
- 每批摘要都要额外调用一次模型；
- 剪枝会改动前缀，打断提示缓存。

其中缓存打断对成本影响最大，所以摘要模型怎么选、剪枝怎么触发，是这个插件最需要斟酌的配置。

安装：

```bash
pi install npm:pi-condense@2.11.2
```

插件默认关闭，装完要设 `enabled: true`（或在会话里执行 `/pruner on`）才会工作。配置写在 `settings.json` 的 `contextPrune` 段。全部命令：`/pruner on|off|now|compact|status|stats|tree|settings|model|thinking|prune-on|batching|min-batch-chars|recovery-grace|dedup|protected-tools|protected-paths|help`。

**我的配置**（settings.json 的 contextPrune 段，完整文件见 [`config/settings.json`](../config/settings.json)）：

```json
{
  "enabled": true,
  "showPruneStatusLine": false,
  "summarizerModel": "deepseek/deepseek-flash",
  "summarizerThinking": "off",
  "pruneOn": "agent-message",
  "batchingMode": "agent-message",
  "quietOversizedSkips": true,
  "minBatchChars": 8000,
  "recoveryGraceTurns": 3,
  "summarizerIdleTimeoutMs": 20000,
  "summarizerMaxTimeoutMs": 100000,
  "protectedTools": [
    "ask_user_question",
    "Agent",
    "get_subagent_result",
    "web_search",
    "source_check",
    "get_search_content"
  ],
  "protectedPaths": ["**/skills/**/*.md"],
  "chainCompression": {
    "enabled": false,
    "rollingWindow": 3,
    "stripFinalAssistantThinking": true,
    "fuseRangeSummary": true
  },
  "purgeErrors": {
    "enabled": true,
    "cooldownTurns": 2,
    "minArgChars": 500
  },
  "dedupByContentHash": true,
  "autoBudgetThreshold": null,
  "spillThreshold": 16384,
  "spillPreviewBytes": 2048,
  "budgetTurnDelta": null,
  "frontierGapThresholdTokens": null
}
```

> **⚠️ 调剪枝参数时，同时盯住缓存命中率和摘要成本。** 剪枝会改动会话前缀，影响后续请求能否复用缓存。摘要模型、批量门槛、链压缩开关和 spill 阈值一起决定成本与延迟；改完用 `/pruner status` 和 `/cache graph` 看实际效果。

几个关键取舍：

- **摘要模型用 `deepseek/deepseek-flash`，thinking 设为 off。** 和 pico、会话命名共用同一个执行档模型；pico 开 high 思考，摘要则关掉思考，把延迟和成本压到最低。
- **minBatchChars 调到 8000。** 默认 1000 会让很小的工具输出也过一遍摘要模型，摘要可能比原文还长，纯属浪费。攒够 8000 字符再剪一批，摘要调用次数大幅减少。
- **关闭 chainCompression。** 链级压缩会改写滚动窗口之外的历史链，破坏前缀缓存里原本稳定的部分。现有剪枝已经够用，关掉它换更高的缓存命中率，效果可以在 pi-cache-graph 里验证。
- **protectedTools 保护六个工具**：`ask_user_question`（提问）、`Agent`、`get_subagent_result`（子代理）、`web_search`、`source_check`、`get_search_content`（联网）。它们的输出是做决策的关键依据，剪掉了模型就失去判断基础。2.10.3 起有个例外：带字符串 `path` 参数的受保护调用，同一路径只保留最新一次读取，更早的换成 `[Superseded: …]` stub。这六个工具基本不带 `path` 参数，这条规则主要作用在 `protectedPaths` 上。
- **protectedPaths 只保留技能文件一条。** 2.10.2 起插件默认值是 `["**/skills/**/*.md", "**/gauntlet-overrides.md"]`，显式配置会整体替换默认值。当前只列了技能文件，gauntlet 覆盖文件因此不受保护。
- **spillThreshold 降到 16384。** 超大输出更早被转存到旁路文件，上下文里只留 2KB 预览。
- **summarizerMaxTimeoutMs 收紧到 100000。** 廉价档模型做摘要足够快，缩短超时，避免断断续续的慢速输出流拖慢剪枝。

### 常用参数

| 参数 | 作用 |
|------|------|
| `enabled` | 总开关 |
| `summarizerModel` | 摘要用模型，`default` 复用活跃模型或 `provider/model-id` |
| `minBatchChars` | 批量摘要的最小字符门槛 |
| `pruneOn` | 触发时机：`agent-message` 自动 / `on-demand` 全手动 |
| `protectedTools` | 永不摘要的工具输出（精确名匹配；同名路径只留最新读取） |
| `spillThreshold` | 超长输出的旁路阈值 |

### 参数详解

先说清两个概念，后面的参数都围绕它们：

- **批（batch）**：一组已经执行完的工具调用。每次 flush 时，一批的工具输出交给摘要模型压成一条摘要，原工具输出在上下文里换成一行 stub（`[Summarized in pruner summary, ref t3 …]`），原文存进索引，模型用 `context_tree_query` 按 `t3` 这样的引用取回。
- **链（chain）**：从一条用户消息开始，经过若干轮工具调用，到一条纯文本回复结束的一段对话。链压缩是第二层：把整条旧链中间的助手思考、工具调用参数、stub 全部删掉，只留开头的用户消息、一段 `<compressed-chain>` 摘要和结尾的回复。

配置写在 `~/.pi/agent/settings.json` 的 `contextPrune` 段，`/pruner` 系列命令的改动也会写回这里。

主开关与触发时机：

| 参数 | 默认 | 取值与效果 |
|------|------|-----------|
| `enabled` | `false` | `true`：开始剪枝。只处理开启之后产生的工具输出，开启前的历史不会补剪<br>`false`：不剪枝，工具输出原样留在上下文。`/pruner on` / `off` 切换并写回 |
| `pruneOn` | `agent-message` | `"agent-message"`：助手发出一条纯文本回复（也就是一个任务做完）时 flush 一次。两次 flush 之间前缀不变，缓存持续命中，每个任务大约打断一次缓存<br>`"on-demand"`：从不自动 flush，只在你执行 `/pruner now` 时剪。缓存最稳，但上下文会一直涨<br>无论选哪个，下面三个阈值触发器都可以额外强制 flush |
| `autoBudgetThreshold` | `null` | 上下文占用达到窗口的这个比例（0–1 之间的小数，如 `0.8`）时，在当轮结束强制 flush，不管 `pruneOn`。触发点最高封顶 30 万 token（1M 窗口的模型设 `0.9` 也会在 30 万时触发）。`null` = 关闭。用 `pi -p` 跑单条长任务时建议设上，否则只有最终回复时才会剪 |
| `budgetTurnDelta` | `null` | 单轮占用涨幅达到这个比例（0–1）时强制 flush，用来接住一次超大工具输出造成的突增。比例按 `min(窗口, 30 万)` 计算，`0.1` 在 200k 模型上 = 单轮涨 2 万 token。`null` = 关闭 |
| `frontierGapThresholdTokens` | `null` | 上次剪枝之后积累的未剪工具输出达到这么多 token 时，在轮末强制 flush。按绝对 token 数计，与窗口大小无关；官方建议起始值 80000。只能在配置文件里设。`null` = 关闭 |
| `showPruneStatusLine` | `true` | `true`：底栏显示剪枝状态和回收比例（如 `prune: ON · 92.0k->14.0k (-85%)`），以及排队提示<br>`false`：不显示 |

摘要模型：

| 参数 | 默认 | 取值与效果 |
|------|------|-----------|
| `summarizerModel` | `default` | `"default"`：用当前会话模型做摘要，贵且慢<br>`"provider/model-id"`：用指定模型，通常选便宜快速的模型。指定模型临时故障时自动改用会话模型，之后每 10 分钟试探一次能否切回 |
| `summarizerThinking` | `default` | `"default"`：请求里不带思考参数，由供应商决定<br>`off` / `minimal` / `low` / `medium` / `high` / `xhigh`：指定思考档位。档位越高摘要质量越好，但更慢更贵 |
| `summarizerIdleTimeoutMs` | `20000` | 摘要流超过这么多毫秒没有新数据（包括等首个 token）就中止，按临时故障处理。`0` = 不限 |
| `summarizerMaxTimeoutMs` | `180000` | 单次摘要调用的总时长上限，防止一直慢速吐字不结束。`0` = 不限 |

批的划分与跳过：

| 参数 | 默认 | 取值与效果 |
|------|------|-----------|
| `batchingMode` | `turn` | `"turn"`：每个助手轮（一次带工具调用的回复）单独成一批，各出一条摘要<br>`"agent-message"`：从一条用户消息到最终回复之间的所有轮合成一批，只出一条摘要。摘要调用更少，摘要也更连贯 |
| `minBatchChars` | `1000` | 一批的工具输出总字符数低于这个值就跳过，不调摘要模型，原文留在上下文。`git status`、小文件这类短输出摘要后不会更短，跳过省一次调用。`0` = 不跳过 |
| `quietOversizedSkips` | `false` | `true`：跳过一批时不弹通知（无论是低于 `minBatchChars`，还是摘要比原文还长）<br>`false`：每次跳过都弹通知。跳过本身照常发生 |
| `dedupByContentHash` | `true` | `true`：工具输出与之前已归档的某条完全相同（比如重读没改过的文件）时，直接指向那条的引用，不再调摘要模型<br>`false`：重复输出也照常走摘要 |
| `recoveryGraceTurns` | `3` | 模型用 `context_tree_query` 取回的原文，在上下文里原样保留这么多轮再变回 stub，避免“取回、又被剪、再取回”的循环。`0` = 取回后立即可以再剪 |

保护：

| 参数 | 默认 | 取值与效果 |
|------|------|-----------|
| `protectedTools` | `[]` | 永不摘要的工具名列表，精确匹配，写错的名字会被静默忽略。适合输出要被反复原样引用的工具，如计划、待办、提问结果。被链压缩删掉的段落里如果有受保护的输出，它会被原样搬进 `<compressed-chain>` 里 |
| `protectedPaths` | `["**/skills/**/*.md", "**/gauntlet-overrides.md"]` | 按工具调用参数 `path` 匹配的 glob 列表，命中的调用同样不摘要。`*` 不跨目录，`**` 跨目录，区分大小写。显式设置会整体替换默认值；写 `[]` 关闭 |

受保护的调用有个例外：同一路径被读了多次时，只保留最新一次的原文，更早的换成 `[Superseded: …]`。替换只在剪枝本来就要改写前缀的时候进行，不会额外打断缓存。

链压缩：

| 参数 | 默认 | 取值与效果 |
|------|------|-----------|
| `chainCompression.enabled` | `true` | `true`：超出滚动窗口的旧链做链级压缩，删掉中间的思考、工具调用参数和 stub，回收逐批剪枝动不了的那部分 token；每压一条链，从该链开头起的前缀缓存失效一次<br>`false`：只做逐批剪枝，历史链结构保持不变，缓存更稳。`/pruner compact` 仍可手动压缩 |
| `chainCompression.rollingWindow` | `3` | 最近这么多条已结束的链保持原样，第 N+1 条结束时压缩最旧的那条 |
| `chainCompression.stripFinalAssistantThinking` | `true` | `true`：被压缩链保留的结尾回复去掉思考块<br>`false`：保留思考块 |
| `chainCompression.fuseRangeSummary` | `true` | `true`：一条链里有多条批摘要时，再调一次摘要模型把它们融合成一段连贯摘要<br>`false`：直接把各批摘要拼起来，不额外调模型 |

失败调用清理：

| 参数 | 默认 | 取值与效果 |
|------|------|-----------|
| `purgeErrors.enabled` | `true` | `true`：失败的工具调用，把助手消息里的大段参数（比如写文件失败时的整个文件内容）换成一行占位，错误信息本身保留<br>`false`：失败调用的参数原样保留 |
| `purgeErrors.cooldownTurns` | `2` | 出错后等这么多轮再清理，给模型留出重试的时间 |
| `purgeErrors.minArgChars` | `500` | 参数短于这么多字符不清理 |

超长输出：

| 参数 | 默认 | 取值与效果 |
|------|------|-----------|
| `spillThreshold` | `65536` | 单条工具输出达到这么多字符，在当轮结束时直接把原文写到会话目录旁的文件（`<会话ID>-blobs/`），上下文里只留头部预览和文件路径，不调摘要模型 |
| `spillPreviewBytes` | `2048` | 转存后在上下文里保留的预览字节数 |

图像与请求上限：

| 参数 | 默认 | 取值与效果 |
|------|------|-----------|
| `maxImagesPerRequest` | `null` | 单次请求里的图片超过 N 张时，最旧的图片换成一行文字说明（按 N 的一半分批替换，减少缓存失效），避免撞上供应商的单请求图片上限。`null` = 用内置上限（Anthropic Messages 接口 100 张，其他接口不限）。`enabled: false` 时也生效，只能在配置文件里设 |

## 整体架构

四类插件全部装好后，整体结构如下（比 [01](01-理念与路线.md) 里的版本多了 SubagentWorkflow）：

```
主模型（GPT-6.1 Sol）
  ├─ Agent 工具 → pico 子代理（deepseek-flash）：机械执行、报告写盘
  ├─ SubagentWorkflow：需要时做批量脚本编排
  ├─ ask_user_question：需求不明时弹结构化问卷
  └─ 上下文：pi-condense 剪枝（deepseek-flash 摘要）
              ↓ 观测
  pi-context-view（占用图）+ pi-cache-graph（命中率）+ pi-token-speed（速度）
```

有两处联动要留意：什么时候委托给 pico，规则写在全局 AGENTS.md 里（[09-agents-md.md](09-agents-md.md)）；剪枝改动前缀会直接影响缓存命中，这层关系可以在 pi-cache-graph 里观察（[03-进阶阶段.md](03-进阶阶段.md)）。
