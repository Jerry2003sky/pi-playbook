# 高阶阶段：子代理与剪枝

本阶段的两个插件对 pi 改动最深（定位见 [01-理念与路线.md](01-理念与路线.md)）：子代理带来多代理并行和上下文隔离，剪枝把上下文占用从线性增长压到基本持平。两者都改变了 pi 的工作方式，代价也最明显：子代理要管权限边界，剪枝会让历史细节默认不可见、打断提示缓存。它们放在最后，是因为要靠前面几个阶段打底——比如剪枝的效果要靠缓存监控来验证。

本页内容：**@tintinweb/pi-subagents**（子代理系统）· **pi-condense**（上下文剪枝）

## @tintinweb/pi-subagents —— 子代理系统

> 商店：[pi.dev/packages/@tintinweb/pi-subagents](https://pi.dev/packages/@tintinweb/pi-subagents) · 仓库：[tintinweb/pi-subagents](https://github.com/tintinweb/pi-subagents)

pi 默认单模型、单会话，决策和执行挤在同一个上下文里。任务一大，机械执行的部分会吃掉大量上下文和 token，还会干扰决策。

pi-subagents 引入子代理。主代理用 `Agent` 工具把任务派给另一个独立会话，能力包括：

- 前台阻塞、后台异步、并行执行、定时调度；
- 子代理可以再委托（嵌套）；
- 用 git worktree 隔离代码改动；
- 在输入框里用 `@代理名` 直接点名；
- 运行中途用 `steer_subagent` 纠偏。

批量任务的规模要到运行时才知道时，用 `SubagentWorkflow`：模型写一段确定性的 JavaScript 脚本，用 `agent()`、`parallel()`、`pipeline()` 把子代理串成多阶段流水线。

“便宜模型做执行”靠这套机制落地：大任务里的机械部分交给 flash 级子代理，主模型负责决策和汇总。独立会话隔开了上下文，worktree 可以隔开代码改动；工具执行的权限仍然等同于本机进程的系统权限。

安装：

```bash
pi install npm:@tintinweb/pi-subagents@0.19.0
```

0.19.0 要求 Pi 0.84.0 或更新版本。

配置分两层：

- **持久设置**：全局 `~/.pi/agent/subagents.json`，项目里的 `.pi/subagents.json` 可以覆盖。
- **自定义代理**：每个代理一个 Markdown 文件，YAML frontmatter 定义属性，正文就是它的 system prompt。可以放在 `.pi/agents/<name>.md`（项目级，优先级最高）、`.agents/agents/<name>.md`（项目级共享目录）或 `~/.pi/agent/agents/<name>.md`（全局）；同名时项目级覆盖全局。

**我的配置**：没有 subagents.json，持久设置全用默认值——后台并发 10、前台不限、嵌套深度 2、兜底代理 general-purpose、未指定时后台运行、工作流自动判断。

唯一的自定义是 `pico` 执行代理（[`config/agents/pico.md`](../config/agents/pico.md)）：模型固定为 deepseek 的 `deepseek-flash`，thinking high，`prompt_mode: replace`，不开嵌套委托。它的 `tools` 覆盖了子代理插件识别的全部七个内置工具，所以 Agent 工具描述里显示为 `*`；扩展工具单独加载，嵌套委托由 `allowed_subagents` 控制。设计细节见 [08-agents.md](08-agents.md)。

### 常用参数

| 参数 | 位置 | 作用 |
|------|------|------|
| `maxConcurrent` | subagents.json | 后台代理并发上限（默认 10） |
| `maxConcurrentForeground` | subagents.json | 前台阻塞代理并发上限（默认 0 = 不限） |
| `backgroundByDefault` | subagents.json | 未写 `run_in_background` 的顶层派发是否后台运行（默认 true） |
| `workflowsEnabled` | subagents.json | 是否注册 `SubagentWorkflow`（默认 true，未设置时自动避让其他工作流工具） |
| `maxSubagentDepth` | subagents.json | 嵌套委托深度上限（默认 2），`0` / `1` 全局关嵌套 |
| `fallbackSubagent` | subagents.json | 类型名解析失败时的兜底，`none` 是严格模式直接报错 |
| `model` | 代理 frontmatter | 该代理用的模型，成本控制的第一旋钮 |
| `tools` | 代理 frontmatter | 限定可用的内置工具；插件工具另用 `ext:<扩展>` 前缀筛选 |
| `allowed_subagents` | 代理 frontmatter | 嵌套委托白名单，不开则子代理不能再派发 |

### 参数详解

#### 持久设置（subagents.json）

全局 `~/.pi/agent/subagents.json` 只能手写，`/agents → Settings` 菜单改的值写进项目的 `.pi/subagents.json`；两者都有的字段以项目为准。文件不存在时全用默认值，单个字段非法时只丢弃该字段。注意几个键名和菜单里的叫法不同：调度开关是 `schedulingEnabled`，合并通知方式是 `defaultJoinMode`，状态挂件是 `widgetMode`。

并发与轮数：

| 参数 | 类型/默认 | 说明 |
|------|-----------|------|
| `maxConcurrent` | number，10（1–1024） | 后台子代理最多同时跑几个，超出的排队，有空位自动开始。嵌套子代理和工作流里的子代理不占这个池 |
| `maxConcurrentForeground` | number，0（0–1024） | 前台子代理（调用方阻塞等结果的）最多同时跑几个。`0` 不限：模型一条消息里发出的多个前台 `Agent` 调用会同时启动。用本地模型时，并行代理会互相挤掉提示缓存，可设个小值 |
| `defaultMaxTurns` | number，0 | 子代理默认最多跑多少轮；`0` 不限。代理文件的 `max_turns` 和调用参数优先 |
| `graceTurns` | number，5（1–1000） | 到达轮数上限后，插件先发一句“立即收尾、给出最终答案”，再给这么多轮宽限；宽限内完成记为 `steered`，超出才强制中止（`aborted`） |
| `maxSubagentDepth` | number，2（0–16） | 嵌套委托的深度上限：主会话是 0，它派出的子代理是 1，子代理再派的是 2。设 `0` 或 `1` 等于全局禁止嵌套，不管代理文件怎么写 |

派发行为：

| 参数 | 类型/默认 | 说明 |
|------|-----------|------|
| `backgroundByDefault` | bool，true | 模型调用 `Agent` 时没写 `run_in_background` 怎么处理：<br>`true`：后台运行，调用立即返回 ID，完成后发通知（与 Claude Code 一致）<br>`false`：前台阻塞，结果直接作为工具结果返回<br>只管顶层派发；嵌套派发总是前台。调用参数或代理文件里写明的值优先 |
| `defaultJoinMode` | `smart` / `async` / `group`，默认 `smart` | 多个后台代理完成时，通知怎么发给主模型：<br>`smart`：同一轮里派出的 2 个以上代理合并成一条通知，单个代理单独通知<br>`async`：每个代理完成就单独通知一次，适合要逐个处理结果的场景<br>`group`：即使只派了一个也按组等待合并，适合知道后面还会继续派的情况<br>合并等待时，第一个完成后最多再等 30 秒，没到齐的先发已完成的部分 |
| `fallbackSubagent` | string，`general-purpose` | 模型给的 `subagent_type` 找不到（拼错、已禁用、大小写冲突）时改派给谁：<br>写某个代理名：改派给它<br>`none`（或 `false`）：严格模式，直接报错并列出可用类型，什么都不启动；后台和定时任务尤其建议用，免得替身代理先跑起来<br>注意默认的 `general-purpose` 带全部工具 |
| `schedulingEnabled` | bool，true | `true`：`Agent` 工具多一个 `schedule` 参数，可以让子代理按 cron、间隔或指定时间以后台方式运行，`/agents → Scheduled jobs` 查看和取消<br>`false`：去掉这个参数（省上下文）、隐藏菜单、停止已有定时任务 |
| `workflowsEnabled` | bool，未设置 | 是否提供 `SubagentWorkflow` 工具：<br>未设置：自动，别的扩展已提供 `Workflow`/`SubagentWorkflow` 工具时本插件让位<br>`true`：无论如何都提供<br>`false`：不注册，模型不知道有这个功能，`/agents → Workflows` 和 `--subagents-workflow-file` 一并失效<br>下次启动 pi 生效 |
| `worktreeIsolation` | bool，true | `true`：允许 `isolation: "worktree"`，子代理在临时 git worktree 里改代码，有改动就提交到 `pi-agent-<id>` 分支<br>`false`：`Agent` 工具去掉 `isolation` 参数，所有途径的 worktree 请求都降级为普通运行。仓库大、复制一份很费时间和磁盘时关掉 |
| `agentMentions` | `model` / `direct` / `off`，默认 `model` | 在输入框开头写 `@代理名 消息` 时：<br>`model`：代理在跑就把消息转给它，已结束就恢复它；还没启动的，由一个看不见的对话副本替你写好 prompt 再启动它，多花一次模型调用和一点等待<br>`direct`：没启动的代理立即启动，你的原话就是它的 prompt，不额外调模型<br>`off`：`@` 只用于附加文件 |
| `rememberAgents` | bool，true | `true`：子代理的会话存成普通 pi 会话文件，在 `/resume` 里挂在父会话下面，过很久也能用 `@代理名` 接着聊<br>`false`：只存在内存里，完成约 10 分钟后就无法再恢复<br>代理文件的 `persist_session` 可单独覆盖 |
| `outputTranscript` | bool，true | 是否为每个子代理在系统临时目录写一份 `.output` 对话记录（JSONL，仅本人可读，重启清空）。不想让记录落盘时设 `false`；代理文件的 `output_transcript` 可单独覆盖 |
| `scopeModels` | bool，false | `true`：子代理的模型要在 pi 的 `enabledModels` 白名单里。模型临时指定了白名单外的模型会直接报错；代理文件写死的或继承父会话的只提示警告、照常运行。白名单为空时不检查<br>`false`：不检查 |
| `disableDefaultAgents` | bool，false | `true`：不注册内置的 `general-purpose`、`Explore`、`Plan` 三个代理，只剩自己定义的 |
| `strictAgentFiles` | bool，false | 代理文件读不了或解析失败时：<br>`false`：跳过并警告<br>`true`：pi 启动直接失败并指出文件，防止悄悄换成另一个同名代理在跑。只在启动时生效 |

界面与统计：

| 参数 | 类型/默认 | 说明 |
|------|-----------|------|
| `widgetMode` | `all` / `background` / `off`，默认 `background` | 输入框上方的运行状态挂件显示哪些代理：`background` 只显示后台代理（前台代理已在工具结果里实时显示）；`all` 全部显示；`off` 不显示 |
| `fleetView` | bool，true | 输入框下方的代理列表：子代理运行时，空输入框按 `↓` 进入列表，回车打开该代理的实时对话，可在里面直接发消息纠偏。`false` 关掉 |
| `showModel` | bool，false | `true`：挂件的运行行加上模型名和思考档位；窄终端会挤掉描述文字 |
| `showCost` | bool，false | `true`：挂件、结果和通知里显示估算费用（如 `~$0.0042`），模型没有价格数据时不显示 |
| `reportUsage` | bool，false | `true`：子代理消耗的 token 和费用计入主会话的统计（footer、`/cost`）；`false` 时主会话只统计主模型自己的花费，大量委托的会话看起来几乎不花钱 |
| `viewerMarkdown` | `off` / `assistant` / `all`，默认 `assistant` | 子代理对话查看器里哪些内容按 Markdown 渲染：`off` 全部原样显示；`assistant` 只渲染助手回复，工具输出原样；`all` 工具输出也渲染（会把脚本里的 `#` 注释当标题等，适合本身输出 Markdown 的工具）。查看器里按 `m` 循环切换 |
| `toolDescriptionMode` | `full` / `compact` / `custom`，默认 `full` | 模型看到的 `Agent` 工具描述：`full` 完整版（默认代理下约 1400 token）；`compact` 精简约 75%，适合小模型或本地模型；`custom` 读 `.pi/agent-tool-description.md`（项目）或 `~/.pi/agent/agent-tool-description.md`（全局），支持 `{{typeList}}` 等占位符，文件缺失时回退 `full`。下次启动生效 |

#### 自定义代理 frontmatter

全字段可选。代理文件写了 `model`、`thinking`、`max_turns`、`inherit_context`、`run_in_background`、`isolated`、`isolation` 时，这些值锁定，模型调用 `Agent` 时传的同名参数无效；没写的才由调用参数补上。

身份与显示：

| 参数 | 类型/默认 | 说明 |
|------|-----------|------|
| `name` | string，文件名 | 代理的类型名，`subagent_type` 和 `@代理名` 都用它，可以和文件名不同；不能含 `:`。和内置代理同名会覆盖内置代理 |
| `display_name` | string，同 `name` | 只改界面上显示的名字，不影响派发 |
| `description` | string，文件名 | 出现在 `Agent` 工具描述里，主模型靠它判断什么任务派给这个代理，要写清楚适用场景 |
| `color` | string，无 | 代理名标签的底色：`red`、`blue`、`green`、`yellow`、`purple`、`orange`、`pink`、`cyan` 等名字，或带引号的 `"#8B5CF6"`；无效值不显示标签色 |
| `enabled` | bool，true | `false` 禁用该代理，常用来在某个项目里隐藏内置代理 |

模型与运行：

| 参数 | 类型/默认 | 说明 |
|------|-----------|------|
| `model` | string，继承父会话 | `provider/model-id` 或模糊名（`haiku`、`sonnet`）。匹配很宽容：`.` 和 `-` 视为相同，日期后缀可省，指定的供应商没有该模型时会找其他供应商的同名模型；都找不到就继承父会话模型，`/agents` 里会标出 |
| `thinking` | `off`/`minimal`/`low`/`medium`/`high`/`xhigh`/`max`，继承 | 思考档位；模型不支持的档位 pi 会自动降级 |
| `max_turns` | number，不限 | 最多跑多少轮，到达后进入 `graceTurns` 收尾；`0` 或不写为不限 |
| `prompt_mode` | `replace` / `append`，默认 `replace` | `replace`：文件正文就是完整的系统提示，不继承 AGENTS.md 等父会话规则，适合独立的专项代理<br>`append`：正文追加到父会话的系统提示后面，代理遵守和主会话一样的规则 |
| `inherit_context` | bool，false | `true`：把父会话的对话历史复制给子代理，它知道之前聊了什么，但更费 token<br>`false`：只看到派发时的 prompt |
| `run_in_background` | bool，不写 | `true` 永远后台、`false` 永远前台；不写跟随 `backgroundByDefault` |
| `persist_session` | bool，不写 | 是否把子代理会话存盘；不写跟随 `rememberAgents` |
| `output_transcript` | bool，不写 | 是否写 `.output` 对话记录；不写跟随 `outputTranscript` |
| `session_dir` | string，pi 默认位置 | `persist_session` 为真时会话文件的存放目录，相对路径从代理工作目录算起 |
| `memory` | `project` / `local` / `user`，不写则无 | 给代理一个跨会话的记忆目录（`MEMORY.md` 索引加若干记忆文件）：<br>`project`：`.pi/agent-memory/<name>/`，可提交给团队共享<br>`local`：`.pi/agent-memory-local/<name>/`，本机专用（应 gitignore）<br>`user`：`~/.pi/agent/agent-memory/<name>/`，跨项目的个人记忆<br>没有 `write`/`edit` 工具的代理只能读不能写 |
| `isolation` | `worktree` / `off`，不写 | `worktree`：在临时 git worktree 里运行，改动提交到新分支，不碰主工作区（但它看不到主工作区未提交的改动，不能用来审查当前 diff）<br>`off`：拒绝 worktree，即使调用方要求<br>不写由调用参数决定 |

工具、扩展与嵌套：

| 参数 | 类型/默认 | 说明 |
|------|-----------|------|
| `tools` | 列表，全部 7 个内置工具 | 代理能调用哪些工具：<br>内置工具名列表，如 `read, grep, find`：只给这些<br>`*` 或 `all`：全部内置工具<br>`none`：不给内置工具（扩展工具仍可能有）<br>`ext:<扩展>` 或 `ext:<扩展>/<工具>`：放行指定扩展的工具；一旦写了任何 `ext:`，没点名的扩展工具都不再暴露<br>写错工具名会报错，不会悄悄少给 |
| `extensions` | `true` / `false` / 列表，默认 `true` | 子代理会话加载哪些扩展：`true` 全部默认扩展；`false` 一个都不加载；列表如 `[mcp, "/abs/path.ts", "*"]` 只加载列出的。它决定加载，`tools` 决定暴露 |
| `exclude_extensions` | 列表 | 在 `extensions` 基础上排除某些扩展（只写名字）。不是沙箱：被排除扩展的初始化代码仍会执行一次 |
| `skills` | `true` / `false` / 列表，默认 `true` | `true` 继承父会话的技能；`false` 不要技能；列表则只把列出的技能预先注入系统提示 |
| `disallowed_tools` | 列表 | 无论别的设置怎样都禁用这些工具，如继承扩展工具但禁掉 `write, edit` |
| `isolated` | bool，false | `true`：封闭专家模式，强制不加载扩展和技能、忽略 `ext:`，只剩内置工具。与 `isolation: worktree`（隔离文件系统）是两回事 |
| `allowed_subagents` | `none` / `all` / 类型列表，默认 `none` | 这个代理能否再派子代理：<br>`none`（或不写、`false`）：不能嵌套，不注入嵌套工具<br>`all`（或 `*`、`true`）：可派任何已启用的代理<br>类型列表：只能派列出的类型<br>子代理按它自己的工具权限运行，所以这个列表等于把被派代理的权限也授予了当前代理，要像选 `tools` 一样谨慎。深度受 `maxSubagentDepth` 限制，`isolated` 代理永远不能嵌套 |

### SubagentWorkflow —— 脚本化编排

少量、事先就能确定的独立任务用 `Agent`；批量、多阶段的任务用 `SubagentWorkflow`，以 JavaScript 脚本编排。它可能一次派出大量子代理，所以使用约定要求：用户明确选择工作流或多代理编排后才运行。

**写法。** 脚本开头必须是纯字面量的 `export const meta = { name, description }`。三个核心函数：

- `agent()`：派发一个子代理；
- `pipeline()`：每一项独立地逐阶段推进；
- `parallel()`：等这一组全部完成再往下走。

优先用 `pipeline()`，只有需要跨项汇总时才用 `parallel()` 这道屏障。`schema` 校验子代理返回的对象，`gate` 用命令的退出码验证结果。

**运行限制。** 脚本在 worker thread 的 `node:vm` 里执行，不能读取当前时间、生成随机数或动态生成代码；需要时间戳就通过 `args` 传进去。并发上限 `max(1, min(16, cpus - 2))`，单次运行最多 1000 个代理，`parallel()` / `pipeline()` 单次最多 4096 项。工作流的并发池和会话的 `maxConcurrent` 相互独立。这些限制是为了保证重放结果确定，安全隔离仍要靠运行环境。

**观察与控制。** 调用后立即返回 task id，工作流在后台运行，完成后走普通的后台通知。`/agents → Workflows` 打开两层面板（阶段 → 代理 → prompt/activity/outcome），快捷键：`x` 停止、`p` 暂停、`s` 跳过（该次 `agent()` 返回 `null`）、`r` 重试、`c` 打开该子代理的对话。

**脚本复用。** 每次调用的脚本都会存到会话目录，改完用 `scriptPath` 重跑。值得保留的脚本放进 `.pi/workflows/`、`.agents/workflows/` 或代理目录的 `workflows/`，之后用 `name` 调用。`resumeFromRunId` 重放同一会话中某次已结束运行里没改动的前缀部分，只在该会话内有效。启动时也可以用 `--subagents-workflow-file=<path>` 直接跑一个脚本。

开关 `workflowsEnabled` 默认开启；不显式设置时处于自动模式，发现别的扩展已经提供了 `Workflow` / `SubagentWorkflow` 工具，就主动让位。

| 参数 | 说明 |
|------|------|
| `script` | 脚本源码 |
| `scriptPath` | 脚本文件路径，优先于 `script` 和 `name` |
| `name` | 已保存的脚本名，在三个 `workflows/` 目录里找 `<name>.js` |
| `args` | 原样传给脚本的 `args` 全局 |
| `resumeFromRunId` | 重放同一会话里某次已结束运行的未变前缀 |

`title` / `description` 两个参数接受但忽略，工作流名字以 `meta` 为准。

## pi-condense —— 上下文剪枝

> 商店：[pi.dev/packages/pi-condense](https://pi.dev/packages/pi-condense) · 仓库：[jjuraszek/pi-condense](https://github.com/jjuraszek/pi-condense)

上下文是长会话里最贵的资源。pi 默认让工具输出一直占着上下文：读过的大文件、跑过的命令、搜过的结果全堆在窗口里，越聊越贵、越聊越慢，最后触发 compact，把整个会话压成一段摘要——这是信息损失最大的处理方式。

pi-condense 改为逐批归档。每次 flush 时，已经用过的工具输出交给摘要模型压成简短的 stub，原文归档到会话本地的索引里；模型需要时，用 `context_tree_query` 按引用取回。历史细节平时不占上下文，要用时又拿得回来，上下文占用因此从线性增长变为基本持平，长会话才撑得下去。

代价有三项：

- 历史细节默认不可见，要靠模型主动按引用取回；
- 每批摘要都要额外调用一次模型；
- 剪枝会改动前缀，打断提示缓存。

其中缓存打断对成本影响最大，所以摘要模型怎么选、剪枝怎么触发，是这个插件最需要斟酌的配置。

安装：

```bash
pi install npm:pi-condense@2.11.2
```

插件默认关闭，装完要设 `enabled: true`（或在会话里执行 `/pruner on`）才会工作。配置写在 `settings.json` 的 `contextPrune` 段。全部命令：`/pruner on|off|now|compact|status|stats|tree|settings|model|thinking|prune-on|batching|min-batch-chars|recovery-grace|dedup|protected-tools|protected-paths|help`。

**我的配置**（settings.json 的 contextPrune 段，完整文件见 [`config/settings.json`](../config/settings.json)）：

```json
{
  "enabled": true,
  "showPruneStatusLine": false,
  "summarizerModel": "deepseek/deepseek-flash",
  "summarizerThinking": "off",
  "pruneOn": "agent-message",
  "batchingMode": "agent-message",
  "quietOversizedSkips": true,
  "minBatchChars": 8000,
  "recoveryGraceTurns": 3,
  "summarizerIdleTimeoutMs": 20000,
  "summarizerMaxTimeoutMs": 100000,
  "protectedTools": [
    "ask_user_question",
    "planmode",
    "Agent",
    "get_subagent_result",
    "web_search",
    "source_check",
    "get_search_content"
  ],
  "protectedPaths": ["**/skills/**/*.md"],
  "chainCompression": {
    "enabled": false,
    "rollingWindow": 3,
    "stripFinalAssistantThinking": true,
    "fuseRangeSummary": true
  },
  "purgeErrors": {
    "enabled": true,
    "cooldownTurns": 2,
    "minArgChars": 500
  },
  "dedupByContentHash": true,
  "autoBudgetThreshold": null,
  "spillThreshold": 16384,
  "spillPreviewBytes": 2048,
  "budgetTurnDelta": null,
  "frontierGapThresholdTokens": null
}
```

> **⚠️ 调剪枝参数时，同时盯住缓存命中率和摘要成本。** 剪枝会改动会话前缀，影响后续请求能否复用缓存。摘要模型、批量门槛、链压缩开关和 spill 阈值一起决定成本与延迟；改完用 `/pruner status` 和 `/cache graph` 看实际效果。

几个关键取舍：

- **摘要模型用 `deepseek/deepseek-flash`，thinking 设为 off。** 和 pico、会话命名共用同一个执行档模型；pico 开 high 思考，摘要则关掉思考，把延迟和成本压到最低。
- **minBatchChars 调到 8000。** 默认 1000 会让很小的工具输出也过一遍摘要模型，摘要可能比原文还长，纯属浪费。攒够 8000 字符再剪一批，摘要调用次数大幅减少。
- **关闭 chainCompression。** 链级压缩会改写滚动窗口之外的历史链，破坏前缀缓存里原本稳定的部分。现有剪枝已经够用，关掉它换更高的缓存命中率，效果可以在 pi-cache-graph 里验证。
- **protectedTools 保护七个工具**：`ask_user_question`（提问）、`planmode`（计划）、`Agent`、`get_subagent_result`（子代理）、`web_search`、`source_check`、`get_search_content`（联网）。它们的输出是做决策的关键依据，剪掉了模型就失去判断基础。2.10.3 起有个例外：带字符串 `path` 参数的受保护调用，同一路径只保留最新一次读取，更早的换成 `[Superseded: …]` stub。这七个工具基本不带 `path` 参数，这条规则主要作用在 `protectedPaths` 上。
- **protectedPaths 只保留技能文件一条。** 2.10.2 起插件默认值是 `["**/skills/**/*.md", "**/gauntlet-overrides.md"]`，显式配置会整体替换默认值。当前只列了技能文件，gauntlet 覆盖文件因此不受保护。
- **spillThreshold 降到 16384。** 超大输出更早被转存到旁路文件，上下文里只留 2KB 预览。
- **summarizerMaxTimeoutMs 收紧到 100000。** 廉价档模型做摘要足够快，缩短超时，避免断断续续的慢速输出流拖慢剪枝。

### 常用参数

| 参数 | 作用 |
|------|------|
| `enabled` | 总开关 |
| `summarizerModel` | 摘要用模型，`default` 复用活跃模型或 `provider/model-id` |
| `minBatchChars` | 批量摘要的最小字符门槛 |
| `pruneOn` | 触发时机：`agent-message` 自动 / `on-demand` 全手动 |
| `protectedTools` | 永不摘要的工具输出（精确名匹配；同名路径只留最新读取） |
| `spillThreshold` | 超长输出的旁路阈值 |

### 参数详解

先说清几个词：插件把已用过的工具输出攒成**批次**，到**flush**（一次剪枝）时交给摘要模型，原始输出换成一行**stub**（`[Summarized … ref t3 …]`），原文存进会话索引，模型用 `context_tree_query` 按 ref 取回。flush 会改写前缀、打断提示缓存，所以“什么时候 flush”是成本的关键。下表的值都写在 `settings.json` 的 `contextPrune` 段，大多也能在 `/pruner settings` 里改。

主开关与触发：

| 参数 | 类型/默认 | 说明 |
|------|-----------|------|
| `enabled` | bool，false | 总开关。`/pruner on` 等价于设为 true 并持久保存。只处理开启之后产生的工具输出，中途开启不会回头剪之前的 |
| `pruneOn` | `agent-message` / `on-demand`，默认 `agent-message` | 平时什么时候 flush：<br>`agent-message`：模型发出最终的纯文字回复（这一轮任务做完）时 flush，一个任务约改写一次缓存<br>`on-demand`：从不自动 flush，只在你执行 `/pruner now` 时剪<br>注意 `pi -p` 这种单次运行只有结尾一次回复，中途不会剪，需要配合下面的预算触发 |
| `autoBudgetThreshold` | 0–1 的小数或 null，默认 null | 额外的强制触发：上下文用量达到“窗口 × 这个比例”或 30 万 token（取较小者）时，在本轮结束立即 flush，不管 `pruneOn`。例如 `0.8`。null 关闭 |
| `budgetTurnDelta` | 0–1 的小数或 null，默认 null | 额外的强制触发：单轮用量涨幅超过“min(窗口, 30 万) × 这个比例”时立即 flush，专门应对一次读入超大输出。例如 `0.1` 在大窗口模型上表示一轮涨 3 万 token。null 关闭 |
| `frontierGapThresholdTokens` | number 或 null，默认 null | 额外的强制触发：还没剪的尾部累计到这么多 token 就在本轮结束 flush，按绝对 token 数算，与窗口大小无关，适合超大窗口模型或长时间自动续跑。官方建议从 `80000` 起步。只能在配置文件里设 |
| `showPruneStatusLine` | bool，true | `true`：底部状态栏显示剪枝状态，如 `prune: ON · 92.0k->14.0k (-85%)`，有异常时附 `diag u/m/o/b` 计数<br>`false`：不显示，也不显示排队提示 |

摘要模型：

| 参数 | 类型/默认 | 说明 |
|------|-----------|------|
| `summarizerModel` | `default` 或 `provider/model-id` | `default`：用当前会话模型写摘要，贵且慢<br>`provider/model-id`：指定一个便宜快速的模型，推荐。指定模型临时故障时，插件自动改用会话模型，每 10 分钟试探一次原模型，恢复后切回 |
| `summarizerThinking` | `default` / `off` / `minimal` / `low` / `medium` / `high` / `xhigh` | 摘要调用的思考档位。`default` 不传这个参数，由供应商决定；档位越高摘要越好，也越慢越贵。写摘要一般 `off` 足够 |
| `summarizerIdleTimeoutMs` | number，20000 | 摘要流多少毫秒没收到任何数据就中止（也约束首 token 等待时间），中止算临时故障，会触发上面的改用会话模型。`0` 关闭 |
| `summarizerMaxTimeoutMs` | number，180000 | 单次摘要调用的总时长上限，防止断断续续一直不结束的流。`0` 关闭 |

批量与质量门：

| 参数 | 类型/默认 | 说明 |
|------|-----------|------|
| `batchingMode` | `turn` / `agent-message`，默认 `turn` | 每次 flush 时怎么切批：<br>`turn`：每个助手轮次（一次工具调用往返）单独一批、单独一条摘要，摘要更细，调用次数多<br>`agent-message`：从一条用户消息到最终回复之间的所有轮次合成一批、一条摘要，调用少、摘要更概括 |
| `minBatchChars` | number，1000 | 一批工具输出总字符数低于这个值就不送摘要模型，原样留在上下文（剪了也省不了多少）。`0` 关闭 |
| `quietOversizedSkips` | bool，false | 跳过一批时（摘要比原文还长，或低于 `minBatchChars`）是否不弹通知；跳过照常发生。小工具调用多、通知刷屏时设 true |
| `dedupByContentHash` | bool，true | `true`：新输出和之前已剪过的某条内容完全相同（重复读同一个未改动的文件、重复 `git status`）时，直接指向原来那条，不调摘要模型<br>`false`：重复内容也照常处理 |
| `recoveryGraceTurns` | number，3 | 模型用 `context_tree_query` 取回原文后，原文保留多少个用户轮次再变回 stub，避免“取回 → 又被剪 → 再取回”的循环。`0` 表示取回后立刻可再剪 |

保护：

| 参数 | 类型/默认 | 说明 |
|------|-----------|------|
| `protectedTools` | 数组，`[]` | 这些工具的输出永不摘要，按工具名精确匹配，拼错不报错只是不生效。适合输出要被原样反复引用的工具（计划、待办、会话 ID 之类） |
| `protectedPaths` | 数组，`["**/skills/**/*.md", "**/gauntlet-overrides.md"]` | 工具参数 `path` 匹配这些 glob 的调用永不摘要（`*` 不跨目录，`**` 跨目录，区分大小写）。显式设置会整体替换默认值，`[]` 关闭 |

受保护的读取有一条例外：同一路径被读了多次时，只保留最新一次原文，更早的变成 `[Superseded: …]` stub（重新读文件即可取回）；这种替换只在缓存本来就要失效的时机进行。

链压缩与错误清理：

| 参数 | 类型/默认 | 说明 |
|------|-----------|------|
| `chainCompression.enabled` | bool，true | 一条“链”是从一条用户消息到最终纯文字回复之间的整段工具往返。`true`：较早的已结束的链整段折叠，只留开头的用户消息、一段 `<compressed-chain>` 摘要和最终回复，连中间的思考、工具调用参数一起回收；每折叠一条链，从该链起的缓存失效一次<br>`false`：只做逐批 stub，不动链结构 |
| `chainCompression.rollingWindow` | number，3 | 最近多少条已结束的链保持原样，更早的才折叠。`/pruner compact` 无视窗口，立即折叠所有可折叠的链 |
| `chainCompression.stripFinalAssistantThinking` | bool，true | 折叠时是否去掉该链最终回复里的思考内容 |
| `chainCompression.fuseRangeSummary` | bool，true | `true`：一条链里有多段逐批摘要时，再调一次摘要模型融合成一段连贯摘要<br>`false`：直接拼接各段，不额外调模型 |
| `purgeErrors.enabled` | bool，true | 失败的工具调用（比如 `write` 带了 30KB 内容却报错）在冷却后把调用参数换成 `<purged-errored-args size="N"/>` 占位，错误信息本身保留 |
| `purgeErrors.cooldownTurns` | number，2 | 出错后等几轮再清理，给模型留重试的机会 |
| `purgeErrors.minArgChars` | number，500 | 参数体小于这个字符数的不清理，不值得替换 |

超长输出与图片：

| 参数 | 类型/默认 | 说明 |
|------|-----------|------|
| `spillThreshold` | number，65536 | 单条工具输出达到这么多字符时，本轮结束就直接存到会话旁的 sidecar 文件，上下文里只留开头预览和文件路径，不经过摘要模型 |
| `spillPreviewBytes` | number，2048 | sidecar 化后在上下文里保留的开头预览字节数 |
| `maxImagesPerRequest` | number 或 null，默认 null | 一次请求携带的图片超过 N 张时，最旧的图片换成一行文字说明（按 N 的一半分批替换，减少缓存失效），避免撞上供应商的单请求图片上限。null 用内置上限（Anthropic Messages 为 100，其他不限）。`enabled: false` 时也生效 |

## 整体架构

四类插件全部装好后，整体结构如下（比 [01](01-理念与路线.md) 里的版本多了 SubagentWorkflow）：

```
主模型（GPT-6.1 Sol）
  ├─ Agent 工具 → pico 子代理（deepseek-flash）：机械执行、报告写盘
  ├─ SubagentWorkflow：需要时做批量脚本编排
  ├─ ask_user_question：需求不明时弹结构化问卷
  └─ 上下文：pi-condense 剪枝（deepseek-flash 摘要）
              ↓ 观测
  pi-context-view（占用图）+ pi-cache-graph（命中率）+ pi-token-speed（速度）
```

有两处联动要留意：什么时候委托给 pico，规则写在全局 AGENTS.md 里（[09-agents-md.md](09-agents-md.md)）；剪枝改动前缀会直接影响缓存命中，这层关系可以在 pi-cache-graph 里观察（[03-进阶阶段.md](03-进阶阶段.md)）。
